# v4.8 版本迭代计划

**版本目标：** 画布节点原生执行 + 工作流能力增强
**预计周期：** TBD
**基础版本：** v4.7（画布 AI 辅助模式）

---

## 背景

v4.7 把"代码执行 / HTTP 请求 / 子工作流"等画布节点做成 **AI 辅助执行**（Claude 通过 Bash/Fetch 工具执行），功能完整但：

- **慢**：每个节点走 AI 推理，单节点延迟 3-10s
- **贵**：每次执行消耗 token
- **不精确**：AI 可能"理解错" prompt，结果不够确定性

v4.8 目标：为高频/高性能场景引入**引擎原生节点执行**，让画布成为"AI 编排 + 原生执行"混合平台。

---

## 核心能力

### 1. 引擎原生 Stage 类型（方案 A）

扩展 `core/workflow/parser.rs` 的 `StageType`：

```rust
pub enum StageType {
    Agent,       // 现有
    UserInput,   // 现有
    Loop,        // 现有
    Shell,       // 新增：直接执行 shell 命令
    Http,        // 新增：直接发起 HTTP 请求
    SubWorkflow, // 新增：调用子工作流
}
```

在 `engine.rs` 的 `execute_stage` 中分发：

- **Shell**：`tokio::process::Command` 执行，stdout/stderr 作为 output，`timeout` + `exit_code` 控制成功失败
- **Http**：`reqwest` 发起请求，status + body 作为 output，支持 headers/body/auth
- **SubWorkflow**：递归调用 `engine.execute()`，处理循环依赖检测

**验收标准：**

- 每个节点类型有独立的执行路径（不再走 AI）
- Shell 节点执行延迟 < 100ms（vs 当前 3-10s）
- HTTP 节点支持 GET/POST/PUT/DELETE、自定义 headers、JSON body
- 子工作流支持变量传递和输出回传

### 2. 画布 toYaml 升级

修改 `canvasStore.ts::toYaml()`，生成 v4.8 引擎可识别的 YAML：

- `shell` 节点 → `stage_type: shell`（不再生成 agent）
- `http` 节点 → `stage_type: http`
- `workflow` 节点 → `stage_type: sub_workflow`

保持向后兼容：导入 v4.7 格式的工作流仍可正常工作（AI 辅助模式）。

### 3. 节点执行模式切换

给 shell/http/workflow 节点的 `NodeInspector` 增加"执行模式"开关：

- **原生模式**（默认，v4.8+）：走引擎原生
- **AI 辅助模式**（兼容）：走 agent + Claude CLI

UI 上显示当前模式，用户可按需切换。

### 4. 执行性能监控

在 `ExecutionsPage` 的 stage_results 里，除了现有的 tokens，增加：

- 执行延迟（ms）
- 执行模式（原生/AI）
- Exit code（仅 shell）
- HTTP 状态码（仅 http）

---

## 非目标（不做）

- 不做可视化节点调试断点（复杂度太高，后续版本）
- 不做节点级别的并行执行（engine 已支持 stage-level 并行）
- 不重构画布数据结构（保持 reactflow 节点 + YAML 序列化）

---

## 风险与缓解

| 风险 | 缓解 |
|------|------|
| Shell 执行的安全性（命令注入、路径逃逸） | 强制在 workspace 目录内执行，禁用 `rm -rf /` 等危险命令 |
| HTTP 节点的 SSRF（请求内网地址） | 加入域名白名单或 allowlist 配置 |
| 子工作流的循环依赖 | 执行时维护调用栈，检测到循环直接拒绝 |
| 向后兼容：v4.7 工作流导入失败 | 保留 AI 辅助模式作为 fallback |
